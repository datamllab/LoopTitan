# Map from methods to mechanisms

The release uses the nine paths in the table below and one variant of them. Paper names appear only in recipes and their `source`. The general core is named by its real state update. The `source`, `preserved` and `adaptations` of each path can be exported directly from [`recipes.py`](../src/moeloop/recipes.py). The paths share public text, softmax top-k dropless MoE and AdamW (the default; Muon is optional, see [Training](training.md)). The exceptions are the two dense paths, `sandwich_spec(dense=True)` and `relaxed_spec(dense=True)`: all their FFNs are dense SwiGLU, with no MoE and no aux. These replacements do not make a full training reproduction of the original papers. `LoopedLM` is the public name of the model class. `RecursiveLM` is a compatibility alias for the same class object. `model.py` defines the class as `LoopedLM`; the links in the table point to that file.

Counting rule. The release has nine published looped recipes, the first nine rows of the table. The last row, the residual split from the LatentLoop paper, is a variant of SMELT, the recipe that it modifies, and not a tenth recipe; `scripts/lineage.py` places it under `phase1/m3`. The frozen configurations count twelve. They are the nine recipes (`recipes/phase1/m3` for SMELT, and `meta`, `foil`, `expert-tying`, `huginn`, `loom`, `ouro`, `sandwich` and `relaxed` under `recipes/methods/`), the three-visit and four-visit SMELT variants (`methods/smelt-v3`, `methods/smelt-v4`) and the residual-split variant (`methods/latentloop-residual`). Each has an AdamW file and a Muon file. `methods/m0-loop` is a control and is outside the count.

Numeric/gradient proofs, native training/resume proofs and HF proofs each have different limits; see the [validation matrix](validation.md) and the [reference baselines](baselines.md). P1/P2 compare only standard MoE and SMELT. C compares only the attention/router owners on a fixed expert pool. The engineering qualification of the first seven paths is not a quality conclusion about these seven. Sandwich, relaxed and the LatentLoop residual variant have no engineering qualification record; run issues #232 and #254 trained them on GPU, exported them to HF and evaluated them. Each P1/P2 pair of arms reached the same 20.486B-label endpoint and completed the full downstream evaluation. The four C arms reached a bounded common endpoint. [Validation](validation.md) gives the mixed ARC direction, the C parameter increments and the single-seed limit. No final recipe is declared from the results. Public evidence cites its original source snapshot; there is no retraining for one common release commit.

Read the per-visit behaviour with [`moeloop.diagnostics`](../src/moeloop/diagnostics.py) (logit lens, residual updates, routing overlap, effective depth). The frozen protocol for comparison across methods is Looped MoE Bench; see [Cost and comparison](comparison.md#looped-moe-bench).

## Survey of related methods

The 47 entries below include baselines, related paradigms and boundary cases. They record only the depth of the literature reading and the source-code review. They are not 47 implementations or training qualifications. The table above is the reference for the real run evidence of the nine release paths and the variant. The other entries do not join the supported set automatically.

Each work relates to several mechanism axes at once: state/layout, call order, component sharing, conditional selection, training objective/gradients and the inference cache. The table below is an entry point.

The runtime review separately checked TorchTitan (pinned and current), Transformers and flame. It also re-checked the training and delivery paths of Foil, LOOM and xLLM; see [TorchTitan](https://github.com/pytorch/torchtitan) and the public implementation of each project.

Quality evidence stays within the tasks, scale, budget and ablation scope of each original paper. An entry with only an abstract read, or with no code found, does not become a verified mechanism.
